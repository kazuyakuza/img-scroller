## Overview

- Shape: a single-purpose Windows desktop GUI application — an image viewer with two-axis folder navigation. No server, no back-end. It ships as a single application binary plus a config file (distribution flow: see `## Data and State` below and [tech.md](tech.md)).
- Three pillars chosen in the brief: egui/eframe GUI, WIC system-codec decoding, and reliance on Windows system registration data (codecs and the "Open with..." program list). Wave 1 landed pillars 1–2 as the open-image slice; Wave 6 landed pillar 3 — the "Open with..." menu (runtime system enumeration, NO internal program database).

## Logical Components

The decomposition below is derived from the v1 features; each component carries a landed/planned annotation. The realized module layout is in `## Module Layout (Implemented)`.

- **Viewer UI (egui/eframe, immediate-mode) — Wave-1 slice LANDED; Wave-2 navigation slice LANDED; 0.2.1 floating-controls UI-fix LANDED**: regular resizable window (title `Images Scroller`, opened ALWAYS MAXIMIZED at launch); the empty state shows ONE big centered "Open…" button (18 pt text, large 180×48 button) that opens the native dialog; with an image open there is NO Open control anywhere. While an image is open — or an empty sibling folder is being browsed — ONE centered floating bottom pill renders above the central surface — a non-space-reserving overlay `Area` anchored bottom-center with a translucent dark frame — holding the message line and four arrow buttons with PAINTED vector-triangle arrows (no font dependency; ←/→ navigate previous/next image, ↑/↓ navigate previous/next sibling folder, each enabled exactly when its navigation seam resolves a destination). In empty-folder browsing mode the blank central surface shows the centered `Empty folder` message while the pill's message line stays empty. Both overlay Areas are stateless surfaces (per-call `egui::Id::unique(...)` ids — no remembered window/layout state) and the painted buttons expose AccessKit button info (`WidgetInfo::labeled(Role::Button, …)`). The pill's Wave-4 control groups — the fullscreen toggle (painted square), the zoom `[+][−][restore-fit]` group, and the fit `[fit-width][fit-height]` group (10 buttons in the row) — are LANDED, and since Wave 4.1 the six keyboard-distinct buttons carry hotkey captions while all ten carry hover tooltips (`src/app/button_hint.rs`); since Wave 4.2 the enabled glyphs AND captions render WHITE with a shared 1-point BLACK outline on every painted icon shape and an 8-offset one-point black ring around caption glyphs (`src/app/pill_style.rs`); the "Open with..." menu entry (the pill's 11th button with its upward popup) is LANDED (Wave 6 — the dedicated "Fast Open-with Service" bullet below).
- **Image Decoding Layer (WIC) — LANDED**: decodes any image format registered as a Windows system codec through the windows-rs COM projection (mechanism: [tech.md](tech.md) → `## WIC Decode and Open-Dialog Mechanism (Implemented)`); no bundled decoders; formats without a system codec are unsupported in v1 (accepted constraint).
- **Navigation Engine — both slices LANDED (horizontal Wave 2; vertical Wave 3)**: horizontal — previous/next sibling image in the current folder (listing: non-recursive parent-folder read, 17-extension whitelist; order: the SYSTEM entry-name order (Wave 5.2 — the system file manager's `StrCmpLogicalW` comparator through the `EntryNameOrder` seam; the dedicated bullet below); list edges stay silently); vertical — the ADJACENT sibling folder under the SAME parent (target image priority: (a) session last-viewed image for folders already visited this session, (b) otherwise ALWAYS the target folder's first image in the SYSTEM entry-name order — NO same-filename attempt, NO other fallback; no skip, no wrap; an image-less sibling folder is entered in empty-folder browsing mode, not skipped).
- **System Entry-Name Order — LANDED (Wave 5.1; mechanism Wave 5.2)**: BOTH navigation axes order entry names by the SYSTEM FILE MANAGER's exact order — Explorer-exact `StrCmpLogicalW` (shlwapi): digit-aware NATURAL/numeric ordering (`(1)`, `(2)`, …, `(9)`, `(10)`, …), case-insensitive, through the cfg-gated `platform` facade (`src/platform/windows_collation.rs` — a 17-line TOTAL comparator: two null-terminated UTF-16 buffers, the `i32` result mapped by `result.cmp(&0)`; NO failure path — the Wave-5.1 `Option`/silent-fallback layer was REMOVED and `windows.rs`'s wrapper delegates directly) — via the UNCHANGED `EntryNameOrder` comparator-as-data seam (`src/name_collation.rs`: `system()` resolves the platform's `compare_entry_names_system` at listing-build time; `with_comparator` injects synthetic comparators in container tests); the pure alphanumeric fallback (lowercase form first, exact-character tie-break) remains the container/stub order ONLY (the stub delegates to it; on the Windows release target it is dead code — recorded as acceptable, cfg-gate cleanup deferred to a maintenance wave); BOTH listings consume the seam (the horizontal sort + `first_listed_image`; the vertical sort + the anchor position reading the SAME stored order), so the first-image and last-viewed rules are unchanged. Root cause (Wave 5.2): BOTH the original code-point order and the Wave-5.1 user-default-locale `CompareStringEx` collation sort digit runs LEXICALLY (`(1)`, `(10)`, `(11)`, …, `(19)`, `(2)`, …) — the operator's real `智乃 (1).jpg … 智乃 (97).jpg` folder proved the expectation is the file manager's natural order.
- **Session Last-Viewed Memory — LANDED (Wave 3)**: `src/last_viewed_images.rs` holds the RAM-only map of the last viewed image per visited folder — created empty with the app, updated at every successful open (the key is the RESOLVED open path's parent folder — D5 canonicalization fact), read for the visited-folder priority, destroyed on app close; no disk persistence in v1.
- **Full-Screen View — LANDED (Wave 4 + Wave-4.1 corrections)**: session `fullscreen_on` flag (default OFF at launch; the window itself opens ALWAYS MAXIMIZED and the release console stays hidden); toggle via F11 and the pill's painted-square button sharing ONE `toggle_fullscreen_and_send_command` action (`src/app/fullscreen.rs`/`fullscreen_button.rs`); ONE chrome gate `full_ui_chrome_is_visible()` hides pill/Open-button/empty-folder-message while ON, leaving only the central image; F11 or ESC exits while ON (while fullscreen OFF, ESC is consumed by the Wave-4.2 ESC-close affordance — the dedicated block below; the F11-delay observation is the OS key-repeat — operator note); arrow navigation and zoom/fit hotkeys remain active while ON (intake is ungated), and successful opens keep fullscreen ON. Every toggle also disarms the Wave-4.2 ESC-close popup.
- **ESC-Close Confirm Popup — LANDED (Wave 4.2)**: while fullscreen is OFF (fresh empty state, image open, empty-folder browsed — every chrome state), the FIRST DISTINCT ESC press arms a centered confirm popup carrying the exact sentence `Press ESC again to close` for 2.0 s (`src/app/esc_close_confirm.rs`); a SECOND distinct press while it is visible sends `egui::ViewportCommand::Close`; held-key autorepeat never counts (the `repeat`-flag filter); an expired popup re-arms on the next press; every fullscreen toggle disarms; fullscreen-ON ESC keeps exiting fullscreen only. Popup state is the session-RAM field `esc_close_popup_expires_at` (Data and State below); the reads/order live in `src/app/keyboard_intake.rs` and the pure helpers/decision in `src/app/esc_close_confirm.rs`. Wave 5.1 fixed the expiry: the popup's deadline needs a SCHEDULED PASS — while armed, `request_expiry_wake` (`esc_close_confirm.rs:141`, called per frame at `:116`) re-requests `request_repaint_after(remaining + 0.05 s)` EVERY pass, because eframe SLEEPS at `ControlFlow::Wait` between events and without the wake the deadline comparison never executes (the shipped 0.5.0 defect: the popup never auto-dismissed); `input.time` stays the single clock for arm AND expiry.
- **Manual Zoom + Fit — LANDED (Wave 4 + Wave-4.1 corrections)**: ONE session `zoom_factor` with the SYMMETRIC bounds [1/8, 8] (floor = 1/ceiling; ×1.25 multiplicative steps; pure math `src/zoom.rs`; app seam `src/app/zoom.rs`) — zoom-out passes whole-image fit and keeps shrinking; steps at a bound clamp SILENTLY (all bound messages removed; the only remaining app message is the unsupported-file failure); the buttons dim via `zoom_can_grow`/`zoom_can_shrink`/`zoomed_off_fit`. The strict Shift+'+' / Shift+'−' aliases accept BOTH the resolved key members AND the typed characters, every member individually shift-gated (`src/app/zoom_alias.rs` since Wave 4.2 — the item-11 real-delivery fix; Wave 5.1 round 2 added the typed `'*'` member — the shifted '+' key on Spanish-class layouts types `*` and egui 0.37 has no asterisk key member; on US-like layouts Shift+8 also zooms in, unshifted `*` stays inert). Fit is NO MODE: `W`/`H` keys and both fit buttons (`src/app/fit_button.rs`, renamed from `fit_mode_button`) funnel through `set_zoom_to_fit_width`/`set_zoom_to_fit_height` and set the factor ONLY (axis-ratio over the whole-image fit via `scaling::fit_width_factor`/`fit_height_factor`, clamped INSIDE the bounds; intake at `viewport_rect().size()`); zoom keeps working from the set level; `0`/restore and every successful open return to fit ×1.0; the per-frame draw size composes `fitted_size × factor` in `src/app_display.rs` (a window resize recomputes the base, NOT the factor — no re-fit).
- **Pan-then-Navigate — LANDED (Wave 5)**: while the zoomed image overflows the window on an axis, that axis's arrow keys PAN on every press (auto-repeats included) by 0.125 of the available axis span (`PAN_STEP_FRACTION`) until the image's edge; AT the edge only a DISTINCT non-repeat press navigates (held keys are absorbed); an axis that fits entirely navigates directly on every press. Pure math `src/pan.rs` (per-axis overflow `max(0, zoomed_draw_size − available)`, the symmetric clamp, at-edge predicates with `PAN_EDGE_TOLERANCE = 0.5`, the pure `arrow_outcome` decision); the controller seam `src/app/pan.rs` (`handle_arrow_key` — the Navigate arm calls the shared `navigate` seam verbatim, so the Wave-3 folder-target rule is unchanged); intake routing in `src/app/keyboard_intake.rs` with the `viewport_rect().size()` available-size intake; the paint consumes the re-clamped offset (`src/app/central_surface.rs` + `src/app_display.rs` — explicit `ui.put` repositioning, no gaps/overscan); the offset resets on EVERY successful open and on restore-to-fit and re-clamps lazily on use; keyboard-only (mouse pan/wheel/drag out of scope in v1); the pill's arrow buttons keep navigate-on-click (`src/app/floating_controls.rs` untouched).
- **Fast "Open with..." Service — LANDED (Wave 6)**: at runtime queries the Windows system via `SHAssocEnumHandlers` (the current file's extension, `ASSOC_FILTER_NONE` — NO app-side filter, so UWP/Store apps are INCLUDED by design) for the handlers registered for that type, drains `IEnumAssocHandlers`, reads each `IAssocHandler::GetUIName`, and feeds the raw names through the pure seam `src/open_with_listing.rs` (blank names dropped; the system enumeration order preserved verbatim — no re-sort; case-insensitive dedup keeping the FIRST occurrence, whose raw position survives as `launch_index`; `RegisteredProgram { display_name, launch_index }`). NO internal program database; zero new `windows`-crate features (the six remain; the DLL audit stayed SET-EQUAL 22). The launcher re-enumerates FRESH per hand-off and invokes the selected handler with `IAssocHandler::Invoke` over an `IDataObject` built from the current canonical file (`SHCreateItemFromParsingName` → `SHCreateShellItemArrayFromShellItem`); every failure collapses into the single static message "Windows could not open this file with the selected program." on the pill's message line. The UI side (user-approved Option A): the pill's rightmost 11th button (painted square-with-emerging-arrow glyph, 36×32, NO hotkey in v1) opens an upward `egui::Popup::menu` (`RectAlign::TOP`) listing the stored programs' display names verbatim inside a `ScrollArea::vertical().max_height(300.0)`; the stored list refreshes ONLY at the two decided points — every successful open and the popup-opening click (the popup reads the STORED list; no per-frame enumeration); with an image open and an empty list the button is DISABLED with the tooltip "No programs registered for this file type"; in empty-folder mode it is disabled with the standard "Open with..." tooltip; the fresh empty state has no pill at all; fullscreen ON hides the whole pill (the existing chrome gate). Mechanism detail: [tech.md](tech.md) → `## Open-with Enumeration and Launcher Mechanism (Implemented, Wave 6)`.
- **Distribution Packaging — planned**: zip-style installer (destination-folder selection; unzips the app binary and config file) plus default-viewer registration helper/guidance — the helper mechanism is deferred.

## Open-Image and Display Flow (Implemented)

1. Launch: CLI argument present → `open_image(path)` runs before the first frame; absent → the empty state's big centered "Open…" button → native `IFileOpenDialog` (owner HWND via `raw-window-handle`).
2. Decode: `platform::decode_image` → WIC factory → decoder from filename → frame → format converter initialized to 32bppRGBA → `CopyPixels` copies from the converter (mechanism detail: [tech.md](tech.md)).
3. Success: state stores path + `DecodedImage`, clears the message, and flags a pending texture upload; the next frame's central-panel paint uploads exactly once and paints the image fit-scaled and centered (per-frame fit recomputation via `scaling::fitted_size`, so window resizes keep the display sane).
4. Failure: `Unsupported`/`Unloadable` → the floating pill's message line shows the unsupported-file message (the pill renders while an image is open or an empty-folder context is browsed); a previously loaded image and the rest of the state stay untouched.

## Navigation Critical Paths

Path 1's open/decode/display slice (Wave 1), Path 2's horizontal sibling-image navigation (Wave 2), and Path 3's vertical sibling-folder navigation (Wave 3) are implemented, as is Path 4's fullscreen/zoom/fit toggle slice (Wave 4, as corrected by Wave 4.1, with the Wave-4.2 pill-styling/alias/ESC-close corrections riding on the same paths) and the Wave-5 pan-then-navigate interplay riding on Paths 2 and 3; Path 5's "Open with..." service is LANDED (Wave 6 — the path below).

1. **Entry**: open an image (Explorer association, file manager, or in-app open dialog) → decode via a WIC system codec → display in the regular resizable window → navigation enabled immediately; no folder pre-registration step exists.
2. **Horizontal navigation (Wave-2 slice LANDED)**: arrow key or UI button → previous/next sibling image in the current folder (listing: 17-extension whitelist; order: the system entry-name order (Wave 5.2 — the file manager's natural order); list edges stay silently) → decode → display; since Wave 5 the KEYS pan first while the zoomed image overflows the window and navigate only at the image's left/right edge (a distinct press); the pill's ←/→ buttons keep the direct navigate-on-click semantics.
3. **Vertical navigation (Wave-3 slice LANDED)**: arrow key or UI button → the ADJACENT previous/next sibling folder under the same parent (no skip, no wrap; silent list edges) → target image chosen by priority: (a) the folder's session last-viewed image if the folder was already visited this session (RAM-only), else (b) ALWAYS the target folder's first image (the system entry-name order); NO same-filename attempt → decode → display through the normal open flow; an image-less sibling folder is entered in empty-folder browsing mode (the blank surface shows `Empty folder`; the vertical listing re-anchors on the browsed folder). Since Wave 5 the Up/Down KEYS pan the overflowing vertical axis first and navigate (the Wave-3 target rule) only at the image's top/bottom edge; the pill's ↑/↓ buttons keep the direct navigate-on-click semantics.
4. **Fullscreen / zoom / fit toggles (Wave-4 slice LANDED, corrected by Wave 4.1)**: the window opens ALWAYS MAXIMIZED at launch with the release console hidden; fullscreen OFF default — F11 or the pill's square toggles ON (header/borders + every control hidden — only the image; F11 or ESC exits while ON; while OFF, ESC arms the Wave-4.2 double-press close popup), OFF restores the standard chrome; zoom in/out steps ×1.25 within the SYMMETRIC [1/8, 8] bounds via `I`/`O` (the Wave-4.2 alias accept-set: shifted key members AND typed characters; plain +/=/− inert) or the `[+][−]` buttons, clamping SILENTLY at both bounds (zoom-out passes fit and keeps shrinking; the buttons dim at their bounds); `W`/`H` keys and both fit buttons set the zoom factor ONE-SHOT to width/height fit (zoom continues from that level; no resize re-fit); restore/`0` and every successful open return whole-image fit ×1.0.
5. **Open with (Wave-6 slice LANDED)**: the pill's rightmost button click → the stored list refreshed at the two decided points (every successful open; this popup-opening click) → the upward popup lists the system-registered programs (the system's enumeration order, display names verbatim) → selecting an entry re-enumerates fresh and invokes the selected handler (`IAssocHandler::Invoke` with the current canonical file's `IDataObject`) → a failure shows the single static launch-failure message on the pill's message line.

## Data and State

- **In memory (Wave-1 landed)**: the open-flow state in `ImagesScrollerApp` — last opened path, decoded RGBA payload, current message text, and the display texture handle — all RAM-only, replaced on each successful open; nothing persisted.
- **In memory (per session; Waves 3–4 and 6 landed)**: the horizontal folder listing, the vertical sibling-folder listing, the browsed empty-folder context, the per-folder last-viewed map, the session `fullscreen_on` flag (default OFF; the launch window itself is always-maximized with the release console hidden) and the session `zoom_factor` (symmetric [1/8, 8] bounds — NO separate fit-mode field exists since Wave 4.1; every fit key/button mutates this one factor only) plus the session `esc_close_popup_expires_at` (Wave 4.2: `Option<f64>` — `None` while the ESC-close popup is not visible, otherwise the absolute input time when it dismisses) and the session `pan_offset` (Wave 5: ONE `egui::Vec2` field carrying the per-axis clamped pan offsets; zeroed on every successful open and on restore-to-fit; re-clamped lazily on use against the current zoom-composed overflow; zoom steps do NOT reset it), and the session `open_with_programs` list (Wave 6: `Vec<RegisteredProgram>` — the stored enumeration of the system-registered programs for the current file's type, refreshed ONLY at every successful open and at the popup-opening click, cleared when empty-folder mode is entered) — all RAM-only, destroyed on close; never persisted in v1.
- **On disk (planned)**: an application **config file** shipped by the installer alongside the binary (brief distribution flow). Its contents/format are **not defined anywhere yet** — only its existence is recorded here; contents are an implementation decision.
- No other persistent state in v1; explicitly no persistence of the last-viewed memory.
