## Image Format Support

- The app opens any image whose format is registered as a codec in the Windows system (via WIC), e.g. jpg, png, bmp, gif, webp, and heic when a system codec is installed.
- Formats not registered in the system are **not supported in v1** — the accepted constraint of relying on system codecs.

## Dependencies (Landed, Wave 1)

Landed in `Cargo.toml` (every pin is exact `=`; every harness cargo invocation runs with `--locked`):

## WIC Decode and Open-Dialog Mechanism (Implemented)

Implemented in `src/platform/windows.rs` via the windows-rs COM projection (`windows` crate =0.62.2), cfg-gated behind the `platform` facade (non-Windows builds compile `src/platform/stub.rs`):

- COM initialization: `CoInitializeEx(None, COINIT_APARTMENTTHREADED)`; `S_OK`, `S_FALSE`, and `RPC_E_CHANGED_MODE` all count as initialized.
- Open dialog: `CoCreateInstance(&FileOpenDialog)` → `IFileOpenDialog` with options `FOS_FORCEFILESYSTEM | FOS_PATHMUSTEXIST | FOS_FILEMUSTEXIST`; `Show` receives the owner HWND resolved from the eframe frame through `raw-window-handle` (Win32 handle); the result is read via `GetResult` → `IShellItem::GetDisplayName(SIGDN_FILESYSPATH)` and freed with `CoTaskMemFree`.
- WIC decode chain: `CoCreateInstance(&CLSID_WICImagingFactory)` → `IWICImagingFactory::CreateDecoderFromFilename` (`GENERIC_READ`, `WICDecodeMetadataCacheOnDemand`) → `GetFrame(0)` → `GetSize` → `CreateFormatConverter` → `Initialize` to `GUID_WICPixelFormat32bppRGBA` (dither `WICBitmapDitherTypeNone`, palette `WICBitmapPaletteTypeCustom`) → `CopyPixels` read from the initialized converter (the conversion to straight RGBA materializes during this copy) into an RGBA8 byte buffer.
- Failure classification: `WINCODEC_ERR_COMPONENTNOTFOUND` → `Unsupported`; every other error → `Unloadable`; both surface the single unsupported-file message (constant in `src/image_loading.rs`) in the floating navigation pill's message line (the pill renders while an image is open or an empty-folder context is browsed — mechanism: `## Vertical Navigation and Session Last-Viewed Memory (Implemented, Wave 3)`).

## Horizontal Navigation Mechanism (Implemented, Wave 2)

Implemented in `src/folder_listing.rs` (pure listing logic, container-testable) plus `src/app.rs` / `src/app/floating_controls.rs` (intake and on-screen controls):

- Listing scope: the sibling images of the opened image's folder ONLY — one non-recursive directory read of the opened image's parent; directories are never listed (nested subfolders are not entered).
- Image filter: a fixed 17-extension whitelist (`avif`, `bmp`, `dib`, `gif`, `heic`, `heif`, `ico`, `jfif`, `jpe`, `jpeg`, `jpg`, `jxr`, `png`, `tif`, `tiff`, `webp`, `wdp`), matched ignoring ASCII case. WIC codec availability is NOT probed — an extension-listed file the system cannot decode fails at open time through the normal failure path.
- Order (v1 fixed alphanumeric, no settings UI): file names compare by lowercase form first; names equal ignoring case tie-break by exact characters (e.g. `alpha.gif` < `ALPHA.jpg` < `Alpha.jpg` < `alpha.jpg`).
- Listing state: `ImagesScrollerApp.current_folder_listing` (RAM-only) — rebuilt from the new folder on EVERY successful open; `None` until the first open succeeds.
- Keyboard: `ArrowLeft` → previous, `ArrowRight` → next — and, since Wave 3, `ArrowUp`/`ArrowDown` (vertical axis: the section below) — all evaluated per frame; the arrows navigate DIRECTLY — pan-then-navigate interplay is Wave-5 scope, not implemented here.
- Edge behavior: at the list's first/last position navigation stays silently (no wrap, no message); every "nothing to navigate to" case (no image open, no listing, unresolvable index, list beginning/end) resolves to no neighbor.
- Failure rule: opening a neighbor reuses the Wave-1 `open_image` seam — a failed decode keeps the currently displayed image and shows the unsupported-file message.
- On-screen controls (0.2.1 floating layout per operator-run feedback): ONE centered floating bottom pill — an overlay `egui::Area` anchored bottom-center INSIDE the image window (non-space-reserving; it replaced the 0.2.0 corner rails, whose ←/→/↑/↓ glyph labels rendered as tofu boxes on Windows). The pill holds the message line (12 pt, directly above the button row) and one row of four arrow buttons `[←] [→] [↑] [↓]` whose arrows are painted vector triangles via `egui::Shape::rotated_triangle` — no font dependency (guaranteed-visible icons on Windows 10/11). ←/→ and ↑/↓ all navigate through the same `navigate` seam as the keys (the vertical axis: the section below). A direction button is enabled exactly when the navigation seam resolves a neighbor. The pill renders while an image is open or while an empty-folder context is browsed; on the fresh empty state it is absent by approved design, so a failure message there is never shown.

## Vertical Navigation and Session Last-Viewed Memory (Implemented, Wave 3)

Implemented in `src/sibling_folder_listing.rs` (pure sibling-folder listing, container-testable), `src/app/folder_navigation.rs` (the vertical arm of the shared `navigate` seam), and `src/last_viewed_images.rs` (the memory):

- Enumerated scope: the sibling folders of the opened image's folder — ONE non-recursive directory read of the current folder's PARENT; only immediate child DIRECTORIES of that scope parent are listed (deeper folders are never entered, the current folder itself is excluded, and directory-ness comes from each entry's `file_type`, which leaves symlinked folders unlisted — the sibling listing's symlink-policy test); an unreadable scope parent yields an empty listing, an unresolvable anchor (no parent / missing current folder) yields no listing.
- Order (v1 fixed): the SAME fixed alphanumeric collation as the image listing, now shared via `src/name_collation.rs` (`compare_entry_names`: lowercase form first, exact-character tie-break) — one fixed order for files AND folders.
- Anchor + resolution: the OPENED IMAGE (or, in empty-folder mode, the browsed folder with a placeholder name) is passed verbatim and the module canonicalizes its paths internally (`fs::canonicalize`); resolution is ±1 per direction with `ListBeginningReached`/`ListEndReached` at the list edges — an edge resolves to no neighbor (no wrap, no skip, no message).
- Intake + buttons: `ArrowUp` → previous sibling folder, `ArrowDown` → next, evaluated per frame in `src/app.rs`; the pill's ↑/↓ buttons carry the same directions (accessible labels `Previous sibling folder` / `Next sibling folder`); all four arrows share the one `navigate` seam, and each is enabled exactly when `neighbor_image_path(direction)` resolves Something (per frame; in empty-folder mode the ←/→ image arrows resolve to no neighbor).
- Target-image priority (binding correction — NO same-filename attempt): (a) if the target folder was visited this session → its recorded last-viewed image; (b) otherwise ALWAYS the target folder's FIRST whitelisted image in the fixed collation (the first-listed probe through `FolderListing::first_listed_image`); NO other fallback; an image-less folder resolves to no target → empty-folder mode below; the chosen target always opens through the NORMAL `open_image` flow (a decode failure — e.g. the recorded last-viewed path vanished — keeps the previously displayed image and shows the unsupported-file message).
- Canonicalization (D5): the single normalization point of the open flow is `open_image` — it resolves the opened path through `fs::canonicalize` (raw-path fallback) before the open outcome applies; the last-viewed KEY is that resolved path's parent folder (plain `parent()`, never re-canonicalized) and the vertical listing's folders come from the same canonicalized resolution, so same-folder visits meet the same map entry regardless of path spelling.
- Empty-folder browsing mode (D2-final, as shipped): an image-less sibling folder is ENTERED, NOT skipped — the browsed folder replaces the open image (opened path, decoded payload, horizontal listing and message released; NO last-viewed entry is recorded); the vertical listing re-anchors ON the browsed folder, so ↑/↓ continue from it across both folder kinds while the list edges stay silent; the blank central surface shows the centered `Empty folder` constant (`EMPTY_FOLDER_MESSAGE` in `src/app/empty_folder_view.rs`) — NOT in the pill's message line, which stays empty in this mode; the pill renders while a folder is browsed (visibility gate: image open OR browsed-folder context), a failed open in this mode only updates the pill's message line, and the mode ends at the next successful open (the browsed-folder context is cleared); a vanished browsed folder yields an empty vertical listing (both folder arrows disable, no message).
- Session last-viewed memory: `LastViewedImages` — a RAM-only folder→image map created empty with the application, updated at EVERY successful open, read for the visited-folder priority lookup, and destroyed with the application struct; NO persistence to disk in v1.

## Fullscreen, Zoom and Fit Modes (Implemented, Wave 4)

Landed in Wave 4; the model recorded here carries the binding 2026-11-02 Wave-4.1 operator corrections — the 0.4.0 fit-mode×factor composition, the asymmetric [1.0, 8.0] zoom range, the loose alias chord, and every rejected-step/bound/activation message they contained are SUPERSEDED: `Zoom max`/`Zoom min`/`Fit width`/`Fit height` messages no longer exist anywhere in `src/`. Implemented in `src/zoom.rs` (pure zoom math), `src/scaling.rs` (the one-shot fit factors), `src/app/zoom.rs` (the app seams incl. the alias chord and the one-shot fit sets), `src/app/fullscreen.rs` (the fullscreen flag/gate/layout + ESC exit), `src/app/keyboard_intake.rs` (all per-frame key intake), `src/app/zoom_button.rs`/`src/app/fit_button.rs`/`src/app/fullscreen_button.rs` (the pill groups), `src/app/button_hint.rs` (captions/tooltips), `src/app/central_surface.rs` (the single paint seam), and `src/app_display.rs` (the paint math):

- Launch state (Wave 4.1 Task 1, superseding "launch options untouched"): `src/app.rs` builds `NativeOptions` with `.with_maximized(true)` — the window opens ALWAYS MAXIMIZED at EVERY launch; `src/main.rs` carries `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` — the console window is hidden in RELEASE builds only (a dev `cargo run` console is expected, not a defect). The fullscreen default stays OFF and nothing ever auto-fullscreens.
- Session state (RAM in `ImagesScrollerApp`, never persisted): `fullscreen_on` (default OFF) and `zoom_factor` — ONE multiplicative factor with SYMMETRIC bounds: ceiling 8.0, floor `ZOOM_FACTOR_MINIMUM = 1.0 / ZOOM_FACTOR_MAXIMUM` (≈ ÷8, `src/zoom.rs`), step ×1.25, restore target 1.0. NO mode field of any kind exists (the former `FitMode` tri-state and `set_fit_mode` seam were removed; `ImagePainting` is the 2-field `{ decoded_image, zoom_factor }` request).
- Fullscreen: ONE shared toggle action (`toggle_fullscreen_and_send_command`) flips the flag and sends `egui::ViewportCommand::Fullscreen(bool)` exactly once; the F11 intake (`FULLSCREEN_TOGGLE_KEY`) and the pill's painted-square button both use it; the ONE chrome gate `full_ui_chrome_is_visible()` hides pill/Open-button/empty-folder-message while ON. Wave 4.1 added the ESC exit (`FULLSCREEN_EXIT_KEY = Key::Escape`, pure predicate `escape_exits_fullscreen`): ESC exits fullscreen ONLY while it is ON; while fullscreen is OFF, ESC is consumed by the ESC double-press close affordance (mechanism: `## Wave-4.2 Operator-Feedback Mechanisms (Implemented)` below), and EVERY fullscreen toggle also disarms that popup. The operator's F11 non-immediacy was root-caused agent-side as the OS key-repeat delay with NO timing change (recorded as the OPERATOR-RUN note). Arrow navigation and zoom/fit hotkeys keep working while ON; successful opens keep fullscreen ON; toggling never touches `zoom_factor`.
- Zoom: `I` zooms in, `O` zooms out; the alias layer is strict and PER-MEMBER shift-gated (`src/app/zoom_alias.rs` since Wave 4.2): the Shift-held key members (Equals/Plus → in, Minus → out) AND the Shift-held typed characters ('+'/'=' → in, '-'/`−`/'_' → out) both fire; the PLAIN (unshifted) `+`, `=`, and `-` keys are inert (mechanism: `## Wave-4.2 Operator-Feedback Mechanisms (Implemented)` below). `0` (`Key::Num0`) restores. Every step multiplies/divides by 1.25 between the symmetric bounds; zoom-out PASSES the whole-image fit level and keeps shrinking to the ÷8 floor (binding correction); a step past a bound clamps SILENTLY — no message is ever announced for zoom/fit actions (the ONLY remaining pill message is the unsupported-file failure text). Button enablement: [+] dimmed exactly while `zoom_can_grow()` is false (at the ceiling), [−] dimmed exactly while `zoom_can_shrink()` is false (at the floor), restore-fit dimmed exactly while `zoomed_off_fit()` is false (factor == 1.0).
- One-shot fit (Wave 4.1 Task 7, replacing the Wave-4 mode model): `W`/`H` keys AND both fit buttons funnel through the ONE seams `set_zoom_to_fit_width`/`set_zoom_to_fit_height` (`src/app/zoom.rs`) — each computes the axis-fit factor AT INTAKE from the current available size (`egui::viewport_rect().size()`; egui 0.37 removed `screen_rect`, so the intake decision reads the full viewport rect) as an axis-ratio over the whole-image fit via `scaling::fit_width_factor`/`fit_height_factor`, clamped INSIDE the symmetric bounds through the ONE shared clamp `crate::zoom::clamped_zoom_factor`, and sets `zoom_factor` ONLY. The set is silent; it no-ops without an open image; afterward normal zoom in/out works FROM that level (nothing blocked); a repeated set recomputes; `0`/restore and EVERY successful open reset to 1.0; and the display keeps composing `fitted_size(current available) × zoom_factor` per frame, so a window resize after a set does NOT re-fit.
- Intake: `src/app/keyboard_intake.rs` runs the one per-frame read in fixed order (F11 → ESC-exit-fullscreen → the ESC-close non-repeat ESC scan → zoom-in → zoom-out → restore `0` → `W` → `H` → the four arrows), with the per-frame ESC-close popup-expiry update running between the reads and the dispatch, dispatch mirroring the reads (the ESC branch is an if/else — the fullscreen-ON exit keeps priority, the `else` routes the Wave-4.2 ESC-close arm/close decision), in EVERY mode and always BEFORE the layout dispatch.
- Display: `ImagePainting { decoded_image, zoom_factor }` (2 fields, `src/app_display.rs`) → `fitted_size` scaled by `zoomed_draw_size` every frame; zoomed overflow clips so the CENTER stays visible (no pan — Wave 5); BOTH paint surfaces route through the single `src/app/central_surface.rs` seam; texture discipline unchanged (one upload per decode).

## Wave-5 Pan-then-Navigate Mechanism (Implemented)

Landed in Wave 5 (branch `feat/wave-5-pan-then-navigate`, version 0.5.0). Implemented in `src/pan.rs` (pure math), `src/app/pan.rs` (the controller seam), `src/app/keyboard_intake.rs` (arrow routing), `src/app/zoom.rs` (the restore-path reset), `src/app.rs` (the session state + the open-path reset), `src/app/central_surface.rs` + `src/app_display.rs` (the paint composition); `src/app/floating_controls.rs` is UNTOUCHED — the pill's arrow buttons keep the pre-existing navigate-on-click semantics and neighbor-based enablement (keys-only pan):

- Pure math (`src/pan.rs`): per-axis overflow = `max(0, zoomed_draw_size − available)`; the symmetric [-limit, +limit] offset space around center (`axis_pan_limit` = half the overflow; `clamped_axis_offset` collapses to 0 without overflow); at-edge predicates `axis_is_at_negative_edge`/`axis_is_at_positive_edge` with tolerance `PAN_EDGE_TOLERANCE = 0.5`; the pan step `PAN_STEP_FRACTION = 0.125` × the available axis span per press (a window-fraction step); and the pure `arrow_outcome` decision — a fits-entirely axis navigates directly on EVERY press (repeat included); an overflowing axis pans on EVERY press until its edge; AT the edge a DISTINCT non-repeat press navigates and a held auto-repeat is absorbed.
- Controller seam (`src/app/pan.rs`): `ArrowKeyPress { direction, repeat }`; `non_repeat_arrow_press_occurred` (the repeat-flag filter — the Wave-4.2 ESC non-repeat precedent); `arrow_pan_axis`/`arrow_pan_sign` map the direction to its axis/sign; `handle_arrow_key` evaluates the axis overflow from `zoomed_draw_size` vs the `viewport_rect().size()` intake and applies the outcome — `Pan` writes the offset through `apply_pan_delta` with the WRITE-side clamp (`clamped_axis_offset(raw + signed_delta, overflow)` at `src/app/pan.rs:126` — the last step lands exactly on the edge); `Navigate` calls `self.navigate(press.direction)` VERBATIM (the Wave-3 folder-target rule referenced unchanged).
- Intake routing (`src/app/keyboard_intake.rs`): the four arrow reads and dispatches route through `handle_arrow_key`; the available-size intake is `screen_context.viewport_rect().size()` (6 intake sites total: 2 fit + 4 arrows).
- Reset contracts: `pan_offset: egui::Vec2` (ONE session-RAM field carrying both per-axis components, never persisted) is zeroed on EVERY successful open (`accept_open_outcome`, `src/app.rs:95`) and on restore-to-fit (`reset_pan_offset` at `src/app/pan.rs:65`, called from `restore_zoom_to_fit` at `src/app/zoom.rs:74` — both the `0` key and the pill's restore-fit button funnel there). Zoom steps and one-shot W/H fit sets do NOT reset the offset (pinned by tests).
- Re-clamp contract (lazy-on-use): NO clamp call exists in the zoom actions BY DESIGN — the paint re-clamps the offset EVERY frame against the CURRENT zoom-composed overflow (`src/app_display.rs`: `zoomed_draw_size` → `axis_overflow_pair` → `clamped_pan_offset`), and the next arrow write re-clamps at `src/app/pan.rs:126`; a zoom/factor change that grows or shrinks the overflow is therefore absorbed without a reset.
- Paint composition (`src/app/central_surface.rs` + `src/app_display.rs`): `ImagePainting` gained the `pan_offset` field (the 3-field `{ decoded_image, zoom_factor, pan_offset }` request); the paint positions the zoomed draw size with an explicit `ui.put` repositioning derived from the clamped offset — no gaps, no overscan; texture discipline unchanged (one upload per decode).
- Deferred-decision outcomes (the todo's deferred list, ALL settled this wave): pan step = 0.125 window fraction; auto-repeat contract = pan accepts repeats, edge-navigation needs a distinct non-repeat press, held-at-edge repeats are absorbed (the OS-repeat timing caveat is the Wave-4.1 F11 precedent note — repeat timing is OS-owned); mouse pan/wheel/drag = NOT in v1 scope (keys-only v1 per the brief — OUT-OF-SCOPE note); fit-mode suppression = MOOT (no `FitMode` exists since Wave 4.1 — one-shot W/H only sets the factor and pan follows the same overflow rule).
- Verification (Wave-5 B-Task 4): dev checks `ALL CHECKS PASSED` — 150 unit tests, 0 failed, across 23 test files (census: `## Testing`); the 0.5.0 exe rebuilt at `dist/windows-x64/img-scroller.exe` = 19,606,124 bytes; the DLL import audit SET-EQUAL to the recorded 22-DLL constant (the list is NOT duplicated here — docs-split rule); NO dependency changes (`Cargo.toml`/`Cargo.lock` untouched by the wave).

## Development Environment and Setup

- The Rust toolchain (stable, with rustfmt and clippy) exists ONLY inside the container image `img-scroller-rust:latest` (pinned base `rust:1.99.1-bookworm`) — nothing is installed on the host; the host needs no Rust/Cargo. Never install tools globally — in-project/container installs only (rule: [`.kilo/rules/never-global-installs.md`](../../.kilo/rules/never-global-installs.md)).
- The image also carries the MinGW-w64 x86-64 GNU cross toolchain (linker `x86_64-w64-mingw32-gcc`; `x86_64-w64-mingw32-objdump` backs the Windows import audit) and the rustup target `x86_64-pc-windows-gnu`.
- Agents reach the VM through the `alpine-vm` MCP: call `vm_status` first, then run commands; the command's exit code is the authoritative evidence; cargo stderr may be absent in captured MCP output (an absent stderr is NOT a failure signal). Full usage notes: [docs/build.md](../../docs/build.md).

## Build Environment (Container on the Alpine VM)

Build-environment decision recorded 2026-10-30 (source: [`.agent/todos/20261030/20261030-todo-1-DONE.md`](../todos/20261030/20261030-todo-1-DONE.md) → "Build Environment Definition"; user decisions bound in the container-harness plan). **Landed in Wave 1 Task 1 (2026-10-31)**: every harness file and both build guides exist and are exercised.

- Container/VM model: ALL Rust/Cargo commands (builds, checks, tests) execute inside a Linux container on the Alpine VM. The host machine that runs the AI agents does NOT need Rust or Cargo installed — the Rust toolchain exists only inside the container image, so the toolchain notes in `## Development Environment and Setup` above describe the toolchain shipped inside the container image, not a host install.
- Project share: the project is shared on the VM at `/img-scroller`; the container working directory is `/img-scroller`.
- Docker prerequisites: Docker with the Compose plugin is available ONLY on the VM — never on the host.
- Access pattern for AI agents: the VM is reached through the `alpine-vm` MCP — call `vm_status` first, then run commands; the command's exit code is the authoritative success evidence; cargo stderr may be absent in the MCP captured output (an absent stderr is NOT a failure signal). If the VM or the `/img-scroller` share is unavailable, STOP the task and return a question to the caller/user.
- Cargo invocations across all waves run through the container harness (`docker compose -f /img-scroller/docker-compose.yml …`); usage is documented in [docs/build.md](../../docs/build.md).
- Base-image pin (landed): official `rust:1.99.1-bookworm` → image name `img-scroller-rust:latest`; rebuild only after a Dockerfile change; toolchain upgrades are plan-gated.
- Named volume (landed): `img-scroller-cargo-target` mounted at `/cargo-target` via `CARGO_TARGET_DIR=/cargo-target` — intermediate Cargo output never lands in the repository; the only tracked root-level build artifact is `Cargo.lock`.
- Lock/artifact policy: `Cargo.lock` is tracked in git; every harness cargo invocation uses `--locked`; produced artifacts stay in the gitignored `dist/` (release `.exe`) and check logs in the gitignored `logs/`/`logs/checks/` — the repo root `.gitignore` contains `dist/`, `logs/`, `*.log`, and `target/`.
- Validation stance: validation is container-only — agent-side Windows GUI/runtime execution is impossible from the Linux container; runtime/GUI validation is OPERATOR-RUN on the real Windows 10/11 machine.
- Harness landing (DONE, Wave 1 Task 1): `Dockerfile`, `docker-compose.yml`, `scripts/dev-checks.sh`, `scripts/build-windows.sh`, `docs/build.md`, `docs/build-windows.md` all exist and are exercised (Task 5: `ALL CHECKS PASSED`; cross-build exit 0 → non-empty `dist/windows-x64/img-scroller.exe`).
- Import audit (DONE, Wave 1 Task 5): the OBSERVED 22-DLL import list of the produced exe is recorded in `scripts/build-windows.sh` (`OBSERVED_DLL_IMPORT_LIST` constant) and in [docs/build-windows.md](../../docs/build-windows.md) → "Static-linking / import audit (retained scope)"; this file deliberately does NOT duplicate the list (docs-split rule). ## Build and Run

- Dev checks: build the image once (`docker compose -f /img-scroller/docker-compose.yml build rust`), then run `docker compose -f /img-scroller/docker-compose.yml run --rm rust sh scripts/dev-checks.sh` — fmt/check/test/clippy in fixed order, final `ALL CHECKS PASSED` (exit 0) / `N CHECK(S) FAILED` (exit 1); full semantics (per-check fallbacks, `FORCE_FAIL`, log path, MCP notes): [docs/build.md](../../docs/build.md).
- Windows x64 release: `docker compose -f /img-scroller/docker-compose.yml run --rm rust sh scripts/build-windows.sh` — runs `cargo build --release --locked --target x86_64-pc-windows-gnu` and leaves a non-empty `dist/windows-x64/img-scroller.exe`; full guide (typed failures, overwrite behavior, audit): [docs/build-windows.md](../../docs/build-windows.md).
- Dev launch: `cargo run` works inside the container for the compile path, but the container has no display server — the GUI window only runs on a Windows machine (operator-run validation).
- x86 release: NOT built in Wave 1 — belongs to Wave 7 (extend `scripts/build-windows.sh` + add the i686 MinGW toolchain when realized).

## Technical Constraints

- Windows-only application (Windows 10/11); x64 + x86 builds.
- Format support depends on the user's system codecs — unsupported formats exist by design.
- No bundled image decoders.
- The per-folder last-viewed memory is session-only, RAM-held, destroyed on close — **no persistence to disk in v1**.
- v1 sort order is fixed alphanumeric — no settings UI.
- Fullscreen, zoom, and fit-mode keybindings, steps, and messages are implementation decisions recorded in the mechanism sections above (the Wave-4 section and `## Wave-4.2 Operator-Feedback Mechanisms (Implemented)`), together with the ESC double-press close mechanism; they are technology constraints of the brief only in session-only form (no persistence). The pan-then-navigate policy (per-axis overflow, the 0.125 window-fraction step, the distinct-press edge navigation, the reset/re-clamp contracts, and the keys-only scope) is recorded in `## Wave-5 Pan-then-Navigate Mechanism (Implemented)` above.
