## Overview

Images Scroller is a Windows desktop image viewer built in Rust. It recreates the behavior of the classic Windows "gallery"-era image viewer: open one image and navigate horizontally across the sibling images in the same folder, and vertically across the sibling folders under the same parent folder. Both axes are driven by arrow keys and by on-screen UI buttons. Opening any image — from Explorer, a file manager, or the in-app open dialog — immediately enables this navigation in its location, with no folder pre-registration or setup of any kind.

## Problem Statement

Modern Windows image viewers lack the classic gallery-style scrolling behavior: after opening an image, the user cannot move to the next/previous image or jump to sibling folders with simple arrow keys in the intended way. Existing alternative viewers that attempt this behavior require the user to pre-register or pre-add the folder to the application before browsing — added friction.

The consequence is that browsing a library of image folders (for example, a photo archive organized as `parent\folder1`, `parent\folder2`, ...) requires manual navigation or a file manager instead of direct in-viewer scrolling.

Therefore, this project provides a viewer that treats any opened image as the entry point into its folder tree, with zero folder setup.

## v1 Features

The v1 scope is exactly the seven features below, as defined in the project brief ([.agent/project-info/brief.md](.agent/project-info/brief.md)); the brief holds the full detail for each one.

1. **Open Image with System-Registered Formats** — opens any image whose format is registered as a codec in the Windows system (e.g. jpg, png, bmp, gif, webp, and heic when a system codec is installed); the image opens in a regular resizable viewer window.
2. **Horizontal Scroll (Sibling Images)** — left/right arrow keys and the floating bottom pill's ←/→ buttons navigate to the previous/next sibling image in the same folder; the scope is strictly the current folder (not recursive); the order follows the SYSTEM's name order — the same order the Windows system (e.g. a file manager) shows for those names, including non-ASCII/Japanese names (the binding 2026-11-12 operator corrections: the order is the SYSTEM FILE MANAGER's exact order — digit-aware NATURAL/numeric ordering (the operator's real `智乃 (1).jpg … 智乃 (97).jpg` folder navigates `(1)`, `(2)`, …, `(9)`, `(10)`, …), case-insensitive, the `StrCmpLogicalW` comparator since Wave 5.2 — not raw character codes and not lexical digit runs; the pure lowercase-form alphanumeric fallback is kept for container/stub builds only); at the first/last image the viewer stays on it (no wrap-around). The floating bottom pill appears while an image is open or while an empty sibling folder is being browsed; its ←/→/↑/↓ arrows are drawn as painted vector triangles (never font glyphs — they render identically on any Windows system regardless of installed fonts), and the up/down folder arrows navigate to the previous/next sibling folder under the same parent (each arrow is enabled exactly when its direction resolves a destination).
3. **Vertical Scroll (Sibling Folders)** — up/down arrow keys and up/down UI buttons navigate to the previous/next sibling folder under the same parent folder; when moving to a sibling folder, the target is (a) the folder's session last-viewed image if the folder was already visited this session (RAM-only), otherwise (b) ALWAYS the target folder's first image in the system's name order — no other fallback; the app also remembers the last viewed image per visited folder for the current session (RAM-only, destroyed on app close — no persistence to disk in v1). An image-less sibling folder is NOT skipped: navigation enters it in an empty-folder browsing state — the open image is released, the blank viewer surface shows the centered "Empty folder" message, and the up/down controls keep moving between sibling folders from there (no wrap-around; at the first/last sibling folder the viewer stays).
4. **Fullscreen Mode** — default OFF at launch: the window opens ALWAYS MAXIMIZED at every launch (binding 2026-11-02 operator correction; never auto-fullscreened), and while the release build runs no console window is visible. When OFF, the floating bottom pill and all other UI controls are visible and the image takes almost all of the central space. Toggling shares ONE action between the F11 keyboard shortcut and the pill's painted fullscreen-square button; the first press turns fullscreen ON — the window header/borders and ALL UI controls (the pill included) disappear and only the image shows, while the arrow keys keep navigating images/folders; F11 — or ESC — exits fullscreen while ON. Outside fullscreen, ESC opens the close confirmation: the first press shows a CENTERED "Press ESC again to close" popup for 2 seconds — the popup DISMISSES ITSELF after those 2 seconds (the binding 2026-11-12 correction: it previously never auto-dismissed on real Windows because the app was asleep between events); a SECOND DISTINCT press while it is visible closes the application — two presses, never held/autorepeated, and the next press shows the popup again after it expires. Fullscreen toggling never touches the zoom state.
5. **Zoom In/Out and Fit Levels** — zoom in/out via the keyboard (`I` zooms in, `O` zooms out; strict shifted aliases: Shift+'+' or Shift+'=' zooms in, Shift+'−' zooms out — recognized on BOTH the key and the typed-character channels of real keyboard input (the binding 2026-11-07 correction: the 0.4.1 chord never fired on the Windows delivery), and since the binding 2026-11-12 round-2 correction the SHIFTED '+' key zooms in on every layout: on Spanish-class layouts (where '+' sits unshifted on its own key) Shift+'+' types the `*` glyph, which is accepted — the set stays layout-agnostic, and the documented side effect is that on US-like layouts Shift+8 (which types the same `*` glyph) also zooms in; the plain unshifted `+`, `=`, `*`, and `-` keys do nothing) and via the pill's [+][−] buttons; every step multiplies/divides by 1.25 within the SYMMETRIC fixed bounds — from ×8 of the whole-image fit at the ceiling down to ÷8 of it at the floor (binding 2026-11-02 correction: zoom-out is NOT blocked at the neutral fit level and keeps shrinking below it). Steps at a bound clamp SILENTLY — every zoom-bound message was removed; zoom actions never announce a message. The [+]/[−] buttons paint dimmed exactly at their bounds. Zooming scales the image around the window's center; while the zoomed image overflows the window, the overflowing region is drawn and the arrow keys pan it (feature 6 below). The `0` key and the pill's [restore-fit] button return to whole-image fit at ×1.0, and EVERY successful image open resets to whole-image fit at ×1.0 as well. "Fit width" (`W` key or the pill's fit-width button) sets the zoom level ONE-SHOT so the image's width fills the window (it may overflow vertically); "fit height" (`H` key or the pill's fit-height button) sets it so its height fills the window (it may overflow horizontally) — the set is a one-shot SIZE SET, not a mode: normal zoom in/out keeps working FROM the set level, a window resize does not re-fit, the action is silent, and both fit buttons are disabled while an empty folder is browsed. Zoom and fit state are session-only (no persistence in v1).
6. **Pan and Navigate at Image Edges While Zoomed** — (landed in Wave 5) — while the zoomed image is WIDER than the window, the left/right arrow keys pan the image horizontally, and previous/next sibling-image navigation triggers only when panning reaches the image's left or right edge; while the zoomed image is TALLER than the window, the up/down arrow keys pan the image vertically, and sibling-folder navigation triggers only when panning reaches the image's top or bottom edge (the Wave-3 folder-target rule is unchanged). The two axes are independent and may overflow together. On an overflowing axis every press pans — held/auto-repeated presses included — moving the image by 1/8 of the window's size on that axis per press; at the image's edge a DISTINCT press navigates (holding the key against the edge never navigates); when the image fits entirely on an axis, that axis's arrows navigate directly, as before Wave 5. The pan offset resets on every successful image open and on restore-to-fit (the `0` key or the pill's restore-fit button) and re-clamps itself after zoom changes. Keyboard-only: mouse-wheel and mouse-drag panning are out of scope in v1.
7. **Fast "Open with..." Menu** — (landed in Wave 6) the floating bottom pill's rightmost (11th) button opens a popup ABOVE the pill listing the programs the Windows system has registered for the currently viewed file's type, and selecting a program opens the CURRENT file with it. The list is built from system registration data at runtime (`SHAssocEnumHandlers` shell enumeration with no app-side filter — UWP/Store apps are included by design); the app maintains NO internal program database. Each entry shows the program's system display name verbatim, in the system's enumeration order (blank names are dropped and case-insensitive duplicates are deduplicated). The stored list is refreshed at exactly three points — every successful image open, the click that opens the popup, and the `Q` press that opens it (the popup itself reads the stored list; no per-frame enumeration). With no programs registered for the file's type the button is DISABLED and its tooltip reads "No programs registered for this file type"; the button's hotkey is `Q` — pressing `Q` opens the menu exactly like the click (only while the button is enabled and the pill chrome is visible), the caption `Q` renders under the symbol in the shared 9-pt white-with-black-outline style, and the enabled tooltip reads "Open with... (Q)"; while the menu is open ALL other app functionalities are OFF — arrow navigation/pan, the zoom and fit keys and buttons, the fullscreen toggle, and the ESC-close contract all do nothing — and `ESC` or `Q` again closes the menu (`ESC` closes ONLY the menu: it never arms the close-confirmation popup and never exits fullscreen even when fullscreen is ON); clicking outside the menu dismisses it; if the system launch hand-off fails, the pill's message line shows the single static message "Windows could not open this file with the selected program." in WARNING ORANGE (the open-with failure message is the ONLY warning-colored message; every other message keeps the default text color). Since Wave 6.1 the launch data object is built with the documented `IShellItem::BindToHandler` single-item bind — the 0.6.0 shell-item-array route requested `IID_IDataObject` off-contract and failed on real Windows before the launch hand-off (the D1 root cause, fixed in 0.6.1). Since Wave 6.2 the launch works on real Windows: the path handed to the shell item builder is first converted to its shell-parseable form, because the app's stored canonical path is the `fs::canonicalize` output carrying Windows' `\\?\` extended-length (verbatim) prefix, which the shell parsing-name API `SHCreateItemFromParsingName` rejects with E_INVALIDARG (0x80070057) — root-caused 100% on every selection with a caller-authorized diagnostic build and fixed by converting ONLY at the launch hand-off (the stored path and every other consumer are untouched; the image OPENING never depended on the canonical form — the decode runs with the pre-canonicalization path). The diagnostic remains an OPTIONAL build-time module (`diagnostic-launch-log`, OFF by default — the release build never enables it) that writes `img-scroller-diagnostic.log` next to the executable only when explicitly enabled; the released 0.6.2 build runs with zero diagnostic activity.

## Window Title and Fullscreen Name Popup (Wave 8)

The window title always shows the path of the currently visible image and updates on every navigation:

- Maximized (the launch state): the FULL path is shown when it fits completely in the title. Otherwise the file name with its extension is shown completely — or, when the name itself is too long, only its LAST characters are shown, prefixed with `...`. With the remaining space the containing folder is added FIRST, then the drive, with `...` between the drive and the visible folder chain, and more parent folders keep being added (walking up) while they still fit.
- While the window is NOT maximized: ONLY the file name (+ extension) is shown — last-chars-truncated with the same `...` prefix when the name itself is too long.
- With no image open (including while an empty sibling folder is browsed) the title stays `Images Scroller`.
- While fullscreen is ON, on every visible-image change (navigation) a popup at the TOP CENTER of the screen shows the currently visible image's name + extension for 3 seconds.

## Distribution and Installation

Images Scroller is distributed primarily as an executable **wizard installer** for 64-bit Windows, published in the GitHub **Releases** section of the project (https://github.com/kazuyakuza/img-scroller/releases) together with the portable zip packages; packages can also be built from source with the container harness (see [Build and Run](#build-and-run) below and [docs/build-windows.md](docs/build-windows.md)). Each release carries the wizard installer plus the zips, with the release notes summarizing the version's changes. Release artifacts (the version is read from `Cargo.toml`; the current release is 1.1.0):

- 64-bit Windows: the wizard installer `ImagesScroller-1.1.0-windows-installer.exe` (recommended), plus the portable zip `ImagesScroller-1.1.0-windows-x64.zip`
- 32-bit Windows: the portable zip `ImagesScroller-1.1.0-windows-x86.zip` (there is NO 32-bit installer — a 32-bit Windows user cannot run the 64-bit installer's payload, so the x86 zip stays the only 32-bit distribution)

### Install with the wizard installer (recommended)

1. Download `ImagesScroller-1.1.0-windows-installer.exe` from the Releases section and run it.
2. The wizard asks for the destination folder — the default is your per-user `Programs\Images Scroller` folder under `%LOCALAPPDATA%` (remembered across reinstalls). Pick any folder you like: no administrator rights are needed, and everything installs for YOUR Windows account only.
3. The **file-association page** shows one checkbox per supported image type — the 17 types listed below — with NONE preselected: pick exactly the types you want to offer Images Scroller for (for example, only `.png`). The install registers only the types you pick (the "Open with" lists and the Windows Settings "Default apps" visibility). Windows never lets a program set defaults silently, so when at least one type was selected the installer opens the Settings "Default apps" page for you to make the final per-type choice.
4. Finish. The install places `img-scroller.exe`, the config file `img-scroller.toml`, and `LICENSE` in the destination folder and creates a Start Menu shortcut. Double-click the shortcut (or the exe) — the application opens (the window opens maximized; no console window appears).

To remove the app, use the **Images Scroller** entry in Windows' "Installed apps" / Add-or-remove-programs list: the uninstaller removes the installed files, the Start Menu shortcut, and EXACTLY the associations the install created (nothing else is touched).

### Install from the portable zip (portable alternative)

1. Download the zip that matches your Windows architecture (64-bit → `...-x64.zip`, 32-bit → `...-x86.zip`).
2. Right-click the zip → "Extract All..." → pick a NEW, EMPTY destination folder of your choice. That folder IS the install folder: the four files land at its root.
3. Double-click `img-scroller.exe` — the application opens (the window opens maximized; no console window appears).

The config file `img-scroller.toml` ships next to the executable; the current version does not read it (settings arrive in a future version), so there is nothing to configure.

### Make Images Scroller the default image viewer (optional, zip installs)

The wizard installer's file-association page replaces this flow for installer installs; this helper flow applies to ZIP installs, where the helper ships inside the extracted folder. Windows 10/11 do not let any program set a default viewer silently — the final choice is always made by you in Settings. The packaged helper prepares that choice:

1. Double-click `register-default-viewer.cmd` INSIDE the extracted install folder. It registers Images Scroller for YOUR Windows user only (HKCU registry keys; no administrator rights), adds it to the "Open with" lists, makes it visible in Settings → Apps → Default apps, and opens that Settings page for you.
2. On the "Default apps" page, find **Images Scroller** and set it as the default for the file types you want (Windows 11: click the app in the list; Windows 10: use "Set defaults by app").

The 17 image file types (identical for the installer's association page and the helper): `.avif`, `.bmp`, `.dib`, `.gif`, `.heic`, `.heif`, `.ico`, `.jfif`, `.jpe`, `.jpeg`, `.jpg`, `.jxr`, `.png`, `.tif`, `.tiff`, `.webp`, `.wdp`. Whether a given type can actually be decoded depends on the image codecs installed in your Windows system (Windows Imaging Component) — the same constraint the application itself has.

Zip-install helper notes: re-running the helper is safe (it writes the same registration values again); if you MOVE the install folder, run the helper once more so the registration points at the new location; to undo the registration, open a command prompt in the install folder and run `register-default-viewer.cmd --unregister` (it removes only the registry entries Images Scroller created — your files and other programs' registrations are untouched). The full packaged guide is `DEFAULT-VIEWER-GUIDE.txt` in the install folder.

## Build and Run

Images Scroller is a Windows desktop image viewer built in Rust with egui/eframe; image decoding uses the Windows Imaging Component (WIC) system codecs. All Rust/Cargo commands run inside a Linux Docker container on the Alpine VM — the host machine needs no Rust or Cargo installed.

v1 format constraint: the app opens any image whose format is registered as a codec in the Windows system (via WIC — e.g. jpg, png, bmp, gif, webp, and heic when a system codec is installed); formats not registered in the system are not supported in v1.

### Container dev checks (no host Rust/Cargo)

Build the container image once, then run the dev-check harness:

    docker compose -f /img-scroller/docker-compose.yml build rust
    docker compose -f /img-scroller/docker-compose.yml run --rm rust sh scripts/dev-checks.sh

The harness runs `cargo fmt --check`, `cargo check --locked`, `cargo test --locked`, and `cargo clippy --locked -- -D warnings`, then prints `ALL CHECKS PASSED` (exit 0) or `N CHECK(S) FAILED` (exit 1). Full semantics — per-check fallback commands, the `FORCE_FAIL` fault-injection hook, the UTC log under `logs/checks/`, and the `alpine-vm` MCP usage notes — are documented in [docs/build.md](docs/build.md); this README does not duplicate them.

### Windows release cross-builds (x64 and x86)

    docker compose -f /img-scroller/docker-compose.yml run --rm rust sh scripts/build-windows.sh

With NO argument the script builds BOTH release targets (x64 first, then x86); ONE optional argument builds exactly that target (`x86_64-pc-windows-gnu` or `i686-pc-windows-gnu`). Artifacts land at `dist/windows-x64/img-scroller.exe` (x64) and `dist/windows-i686/img-scroller.exe` (x86) — the `dist/` tree is gitignored. Typed failures, the per-target build matrix, and the static-linking import audit are documented in [docs/build-windows.md](docs/build-windows.md).

### Portable zip packaging

    docker compose -f /img-scroller/docker-compose.yml run --rm rust sh scripts/package-windows.sh

Produces ONE flat zip per architecture from the built exes, the config file, the registration helper, and the guidance text: `dist/ImagesScroller-<version>-windows-x64.zip` and `dist/ImagesScroller-<version>-windows-x86.zip` (the version is read from `Cargo.toml`). Running the produced `.exe` — GUI behavior and image-format handling — is validated by the operator on a real Windows 10/11 machine; the Linux container cannot run the Windows GUI.

### Windows wizard-installer build (NSIS)

    docker compose -f /img-scroller/docker-compose.yml run --rm rust sh scripts/build-installer.sh

Builds ONE installer embedding the x64 release exe — build that target FIRST (`sh scripts/build-windows.sh x86_64-pc-windows-gnu`), because the installer consumes `dist/windows-x64/img-scroller.exe`. Artifact: `dist/ImagesScroller-<version>-windows-installer.exe` (the version is read from `Cargo.toml`). The `makensis` (NSIS 3.08) cross-build, the define-injection mechanism, the installer behavior, and the typed failures are documented in [docs/build-windows.md](docs/build-windows.md) → "Windows installer packaging (NSIS)".
